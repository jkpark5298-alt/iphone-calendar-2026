# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

모든 답변과 설명은 항상 한국어로 한다. 코드 주석과 화면 문구도 한국어로 쓴다.

## Commands

- `npm run dev`: Next.js dev server bound to `0.0.0.0:3000`, so an iPhone on the same Wi-Fi can open `http://<PC IP>:3000`.
- `npm run build`: production build. Run it before deploying when you add server routes or native deps (e.g. `sharp`).
- `npm run start`: serve the production build locally.
- `npx tsc --noEmit -p .`: type check. There is no lint script and no test suite.
  - After a route is deleted, `.next/types/validator.ts` can report it as missing until the next dev or build run. That error can be ignored.
- No test runner is installed. Verify changes by running the dev server and checking the page in headless Chrome (Chrome DevTools protocol) or by calling the API routes directly.
  - `scripts/album-merge-check.ts` is a standalone check for album merge logic.
- Node 24 can import `.ts` files directly (type stripping), but only when they have no extensionless relative imports. `lib/googleDrive.ts` qualifies.

**The dev server uses the production Supabase project** (`.env.local`). Any save made while testing writes real data. Use throwaway rows and files (e.g. a large dummy `id`) and delete them afterwards.

## Deploy

- Vercel deploys automatically on push to `main`.
- The working branch is `cursor/personal-album-port`, and it is kept identical to `main`. Push the same commit to both: `git push origin HEAD:main && git push origin HEAD:cursor/personal-album-port`.
- Deploy status: `gh api repos/jkpark5298-alt/iphone-calendar-2026/commits/<sha>/status`.
- Production URL: `https://iphone-calendar-2026.vercel.app`.
- Files use CRLF line endings. Preserve them when editing programmatically.

## Architecture

### One big client page
`app/page.tsx` (~7900 lines) is the whole app.
- A `view` state switches between `calendar | diary | info | schedule | redDate | markDate | theme`. There is no per-view routing.
- Most data access happens in the browser through the anon client in `lib/supabaseClient.ts`.
- Larger features are split out:
  - `hooks/useTravelDiaryGeneralInfoState.ts`: 일반정보수집 (collected web/Instagram info, rich-text paragraphs).
  - `components/InfoIndexPanel.tsx`: 정보 인덱스 list.
  - `components/ThemeBoard.tsx`: theme notes (chip list with pins, full list, save status).
  - `features/personal-album/`: 개인앨범, ported from a separate travel-diary app. It is dynamically imported inside the `info` view and opened with `?personalAlbum=1`.

### Data: Supabase is the source of truth, localStorage is a cache
- Per-day localStorage keys follow `iphone-diary-2026-<type>-MM-DD` (`storageKey()` in `page.tsx`).
- When Supabase is configured, the remote copy wins on load. Local copies matter only for unsynced edits.
- Main tables:

| Area | Tables |
|---|---|
| Diary and info vault (unique `entry_date`) | `diary_entries`, `info_entries` |
| Photos and cards | `diary_photos`, `info_photos`, `info_text_cards` |
| Calendar | `calendar_marks`, `red_dates`, `calendar_schedules` |
| Collected info, themes, index | `general_info_items`, `theme_notes`, `information_entries` |
| Personal album (single JSON row, `session_id='default'`) | `travel_albums_state` |

- Saves use `upsert(..., { onConflict })`, which needs matching unique constraints.
  - The project was migrated in 2026-10 and the constraints went missing; `supabase/migrations/20261021_entry_unique_constraints.sql` restores them.
  - `upsertEntryByDate()` in `page.tsx` falls back to update-then-insert on error `42P10`.
  - The same migration also turned most `id` columns into `text` with **no default**. New-row inserts then fail with `23502` (null `id`).
    - `supabase/migrations/20261021_restore_id_defaults.sql` restores the defaults (`gen_random_uuid()::text`; `red_dates.id` is already an identity column).
    - `upsertEntryByDate` also retries with `id: crypto.randomUUID()` on `23502`.
    - Any other insert that omits `id` (diary/info photos, text cards, marks, schedules) depends on that SQL having been run.
  - Tables whose `id` is generated by the app: `general_info_items`, `theme_notes`, `information_entries`.
- The full schema is not in the repo. Migrations are applied by hand in the Supabase SQL Editor.

### Storage buckets

| Bucket | Contents |
|---|---|
| `info-photos` | `general-info/…` = 일반정보수집 images (`mirror-<sha1>.jpg` = copied remote/Instagram images); date folders = 정보보관소 photos |
| `diary-photos` | Diary photos and `themes/<id>/…` |
| `travel-diary-files` | Album originals under `travel-items/…` (`TRAVEL_DIARY_BUCKET` in `lib/supabaseClient.ts`) |
| `travel-diary-private` | `google-drive-auth.json` (Drive refresh token, service-role only) |

Note: `lib/generalInfoHelpers.ts` has its own local `TRAVEL_DIARY_BUCKET = "info-photos"`. Don't confuse the two constants.

### Sync patterns (keep Supabase egress low; the free plan is 5GB/month)
- **Diary autosave:** debounced (0.7s), serialized save queue. Unsynced text is kept in localStorage with `pending: true` and wins on reload. The `[저장]` button flushes the queue immediately.
- **일반정보수집 polling:** every 30s it calls `GET /api/general-info?probe=1`, a small signature over id/title/category/confirmed/created_at. The full list is reloaded only when the signature changes or 5 minutes have passed. The `general-info:reload` window event forces a reload.
- **Album polling:** checks only `travel_albums_state.updated_at_kst` (`probeTravelAlbumsUpdatedAt`).
  - `loadTravelAlbumsFromSupabase` dedupes concurrent loads and reuses results for 3s.
  - Saves call `forgetRecentTravelAlbumsLoad()` so the pre-save merge always reads fresh data.

### Save UX: nothing may fail silently
Rule: the screen says "저장됨" only after the server answered OK, and a failed save must keep the user's text.
- **Diary:** status line `수정됨 · 아직 저장 전` → `저장 중…` → `✓ 저장됨 · 시각` / `⚠ 실패, 자동 재시도`, plus a `[저장]` button. Text typed while the day is still loading (`diaryContentReadyRef` false) is merged after the server text instead of being dropped.
- **Theme:** `ThemeBoard.saveToServer` chains saves (always sends the latest `notesRef`, so a slow old save cannot overwrite newer text), retries after 5s, and flushes on `pagehide` and when going back to the calendar. `persistThemes` returns `true` only when the server accepted it. Shared status UI: `components/SaveStatusBar.tsx`.
- **일반정보수집:** `handleConfirmGeneralInfo` awaits `syncGeneralInfoItemToSupabase`. On failure it keeps the draft, writes the temp draft and shows a warning (before, it cleared the editor and said "저장 완료" even when the server failed). It also refuses to save while inline `data:` images are still un-uploaded. `POST/PUT /api/general-info` return 413 when `formattedTextHtml` is over 200,000 chars (it used to cut the text silently). The temp draft is also written on `pagehide`/`visibilitychange`.
- **localStorage writes must never throw.** iPhone storage can be full, and an uncaught `QuotaExceededError` in `writeLocalThemes` once left the theme screen empty ("전체 0개"). Wrap every write (`try/catch`). `loadThemeNotesWithStatus` never throws, times out after 12s, and the UI shows `다시 시도`; it does not create/upload an empty "새 테마" when the server could not be read.

### Storage pressure → Google Drive
- `lib/storageUsage.ts` measures **all buckets**; `GET /api/storage-usage?summary=1` exposes it. The quota is `NEXT_PUBLIC_SUPABASE_STORAGE_QUOTA_BYTES` (1e9). Both the UI and the archive logic must use this number.
- At ≥80% usage, two archivers run until usage drops below 70%:
  - **Album photos (client side):** `features/personal-album/utils/albumArchiveMigration.ts` compresses in the browser, uploads through `/api/google-drive/upload`, then rewrites the album JSON.
  - **일반정보수집 images (server side):** `lib/generalInfoArchive.ts` via `POST /api/storage-archive`, triggered by `components/StorageArchiveRunner.tsx` in the layout. Steps: download → `sharp` compress → Drive upload and verify → rewrite `general_info_items` URLs → only then delete the Supabase original. `?force=1&only=<path>` works only when `NODE_ENV !== "production"`.
  - Diary, theme and info-vault photos are not archived.
- `lib/googleDrive.ts` holds one owner connection (`drive.file` scope, folder "개인 앨범").
  - Reconnecting with a different Google account is rejected (`DriveOwnerMismatchError`). Optional allowlist env: `GOOGLE_DRIVE_ALLOWED_EMAILS`.
  - The access-token cache is keyed by refresh token. Keep it that way, otherwise the owner check can be bypassed.
  - `/api/google-drive/status` performs a real token refresh and account check (`healthy`, `reason: "token-revoked"`).
  - Drive photos are served through `/api/google-drive/file?id=` with immutable caching. 일반정보수집 rows store the absolute URL (`driveAbsolutePhotoUrl`) because other apps read that data.
  - The OAuth consent screen (GCP project `travel-501405`) is published to production, which is required to avoid 7-day token expiry. `/privacy` exists for that.

### Rich-text editor images (diary, theme, 일반정보수집)
All three editors are `contentEditable` divs. They share `lib/richImageSlots.ts`, wired up by `enhanceRichInlineImages(editor)`.

- **Inserting photos (all three editors):**
  - Typing `s.` / `S.` / `s1.` inserts an empty slot and opens `components/SlotImagePanel.tsx`, which offers 사진찍기, 사진보관함 and 복사한 이미지 붙여넣기.
  - Tapping an empty slot reopens the panel.
  - The toolbar buttons `사진보관함` and `붙여넣기` also work without typing `s.`.
    - `ensureImageSlot(editor)` reuses the last empty slot, or inserts one at the remembered caret (`selectionchange` → `__lastCaret`, because tapping the toolbar steals the selection).
    - If the paste finds no image, `removeImageSlot` deletes the slot it just created.
  - The panel is `position: fixed` and positions itself above the iPhone keyboard (visualViewport inset). Without a `bottom` it rendered off-screen.
- **Frames:** every image sits in a `.rich-inline-img-wrap` frame (older data may use `.generalInfoInlineImageBlock`).
- **Controls added to each frame:**
  - a delete ×
  - three resize handles: `data-axis` = `x`, `y`, `both`
  - a tools bar `.rich-inline-img-tools` with two buttons: `[크기 조절]` and `[2열로]/[1열로]`
- **Resize is opt-in (iPhone fix):**
  - Tapping an image only selects it (`is-image-selected`) and shows the tools bar.
  - Handles show and react only on a frame with `is-resize-mode`, entered with `[크기 조절]` and left with `완료`, a tap elsewhere, or a tap outside the editor.
  - `resizeHandleAtPoint` only hit-tests handles of frames in resize mode and skips zero-size rects. Before this, always-on handles with a large touch area resized images while scrolling.
- **Saved size:** stored on the frame as `data-resized` / `data-height` plus `--inline-img-width` / `--inline-img-height`. `restoreInlineImageDisplaySize` re-applies it on load.
- **2-column rows:**
  - `.rich-inline-img-row` (grid, 2 columns, 3:4 cover crop). It is created when several images are inserted at once, or with `[2열로]` (`toggleImagePair`).
  - `[2열로]` pairs an image with the next or previous image only if no text or media sits between them (`framesAreAdjacent`).
  - Pairing or unpairing clears custom sizes (`clearInlineImageDisplaySize`).
- **iPhone height cap:** at ≤820px, unresized single images in `.collectPaperEditor` (diary, theme and 일반정보수집) are capped at `max-height: 45vh`, so about two images fit on one screen (rules at the end of `app/globals.css`).
- **Save cleanup:** `readStackedHtml` (`lib/collectClassCell.ts`) runs `stripTransientImageUiHtml` before saving. The tools bar and the `is-image-selected` / `is-resize-mode` / `is-resizing` classes never reach the DB; `enhanceRichInlineImages` re-adds the controls on load.
- **Commit after a change:** call `editor.dispatchEvent(new Event("input", { bubbles: true }))`. The React `onInput` handlers save the content.
- **Testing on iPhone size:** use headless Chrome with `Emulation.setDeviceMetricsOverride` (390×844, mobile) and `Emulation.setTouchEmulationEnabled`, then send `Input.dispatchTouchEvent` taps and drags.
  - To get a test theme without touching real notes, put it in localStorage `iphone-calendar-2026-themes-v1`.
  - Editing it syncs to `theme_notes`, so delete the row afterwards.

### Cells (＋ 칸), paste, and view mode in the editors
- **Cells:** the main editor plus `CollectWhiteCell`s below it. `lib/whiteCellOps.ts` finds the cursor's cell (`activeCellIndex`, with a `focusin` fallback for iPhone toolbar taps).
  - `＋ 칸` inserts below the cursor's cell (end if unknown). `－ 칸` removes the cursor's cell (last cell if unknown).
  - Each cell has ↑ ↓ (`onMove`). ↑ on the first cell swaps its content with the main editor (`moveWhiteCell`).
  - `CollectWhiteCell` fills `innerHTML` only when `initialHtml` actually changed (`appliedHtmlRef`). Without this guard React re-ran the effect when a cell was moved and wiped what the user had typed.
  - Diary and theme use it; 일반정보수집 has its own copy of the add/remove buttons in `Chapter3Info.tsx` (append only, no move).
- **Paste:** `lib/richPaste.ts` (`readPastedClipboard`, `pasteClipboardImages`) is used by diary, theme, 일반정보수집 and `CollectWhiteCell`.
  - Text is always inserted as `text/plain`. Never let the browser paste rich HTML: on iPhone, HTML copied from AI apps came out as mojibake (UTF-8 read as CP949).
  - Images (clipboard files, or `<img>` in the copied HTML) go into a slot created at the cursor (`ensureImageSlot`). `data:` and fetchable URLs become uploaded files; unfetchable remote URLs are inserted as-is. If nothing can be fetched the slot is removed and an alert says so.
- **일반정보수집 view mode:** `✏️ 수정 모드` (white background, black text) / `📖 읽기 모드` (sepia `#f4ecd8`, brown text) switch above the body. It is stored in localStorage `general-info-body-view-mode` and applies to the main editor and its cells (`giEditMode`/`giReadMode`, `CollectWhiteCell viewMode`). Diary and theme are unchanged.
- **Theme list:** chips show pinned themes plus the most recently edited ones (6 total, and the open theme). `전체 N개 ▾` opens a searchable list (recent/name sort, pin, delete). Pins are per device, in localStorage `iphone-calendar-2026-theme-pins` (no DB column).

### Web page reader (일반정보수집)
Under the Instagram URL box there is a second input, `웹페이지 URL (신문·블로그 등)`. The Instagram flow (`/api/extract-url`, 메타 보기, paste handling) is unchanged and must stay so.
- `POST /api/read-url` → `lib/readUrl.ts`: SSRF-checked fetch (manual redirects, 3MB cap, EUC-KR aware), Naver blog URL rewrite, `@mozilla/readability` + `linkedom`, then a tag/attribute whitelist (figure/figcaption flattened, consecutive `<br>` collapsed).
- Images: logo/profile/tiny ones are dropped; the first 5 are copied to `info-photos` with `mirrorRemoteImage` (the rest keep their original URL). Body HTML is capped at 120,000 chars (`truncated` is reported).
- Client: `importWebPageIntoBody` in the hook appends `<h2>title</h2>`, a source line with a link, and the body to the end of the main editor, fills an empty title, and writes the temp draft. Instagram URLs are rejected here with a hint to use the Instagram box.
- Not verified on real Naver news/blog, Daum or Tistory pages. Login/paywalled or JS-only pages return a "본문을 찾지 못했습니다" message.

### Images coming in
- Browser uploads go through `lib/compressImageFile.ts`. `GENERAL_INFO_COMPRESS` (1920px, q0.82, skip under 600KB) is applied inside the general-info `uploadFileToSupabaseStorage`.
- `/api/read-url` (web page reader, see above) copies the first article images the same way.
- `/api/extract-url` copies the og:image (including Instagram, whose CDN URLs expire after a few days) into `info-photos` via `lib/mirrorImage.ts` (server-side `sharp`, SSRF-checked redirects).
- `components/LegacyMediaUrlFix.tsx` rewrites URLs that still point at the old Supabase project (`ykumumrvcapnehafexdl`) to the current one, both in the DOM and in localStorage.

### Testing notes for this repo
- Headless Chrome (CDP) works without extra packages: Node 24 has a global `WebSocket`, so a small script can drive `chrome.exe --headless=new --remote-debugging-port=…`. Use a fresh `--user-data-dir` per run (empty localStorage = "new device"). To simulate a full iPhone storage, patch `Storage.prototype.setItem` with `Page.addScriptToEvaluateOnNewDocument`.
- After editing files the dev server recompiles slowly on the first request (20s+). Warm it with `curl` before driving the page.
- Test data goes into the production Supabase. Use ids like `zz-*` (theme_notes) and a far date for diary rows, then delete the rows and any uploaded files (`diary-photos/themes/<id>/…`, `diary-photos/<date>/…`, `info-photos/general-info/mirror-*`). Before deleting mirror files check they are not referenced in `general_info_items`.
- Do not `taskkill /IM chrome.exe`; it closes the user's own Chrome. Stop the dev server by its port (3000) only.

### API route security
- Routes use `lib/apiSecurity.ts`: `assertAppApiAccess` (same-origin or `Bearer APP_API_TOKEN`), `isSameOriginRequest`, `assertRateLimit`, and `assertSafePublicHttpUrl` (SSRF guard).
- The app has no user login, so same-origin checks are the main protection for routes with side effects.
- Server routes that need full access create a service-role client from `SUPABASE_SERVICE_ROLE_KEY`.
